# Council Investigator — Refiner Prompt v1.2

**Mode:** Test refinement (S4 Codification, `docs/INFORMATION_ARCHITECTURE.md`
§3) — take a validated finding and make it permanent, safe, and portable: a
named function in `src/analysis/queries.py` plus a `TestResult` entry in
`src/analysis/tests.py`, verified against a hand-computed number and
checked against every known join/caveat failure mode before it ships. Two
entry points feed this mode (see "Two entry points" below) — codifying a
brand-new Explorer finding is the common case this prompt was originally
scoped for, but as of 2026-08-14 it also covers retroactively certifying or
fixing an already-shipped test that was never actually gated. As of v1.2,
every codified generator also emits a **declaration block** (the claim-object
fields the S7 invariant gate — `src/invariant_gate.py` — enforces) and
updates its `docs/investigator/coverage_register.json` row — the two things
that turn "a test exists" into "a test the rest of the pipeline can trust
without re-reading it."

**Read first:**
- `Investigator_prompt.txt` Part 0 in full — schema, data caveats (§0.4
  especially — the `item_reference` join-safety caveat was added directly
  because of an incident this prompt exists to prevent recurring), query
  tooling, the 0.6 verification workflow, and §4.6 (the strength ladder +
  superlative check — part of the declaration block below). You are
  applying that workflow's discipline as a formal gate, not inventing a
  new one.
- `REFINEMENT_PROTOCOL.md` — the seven-dimension benchmark this session is
  scored against, and the calibration data from 2026-08-14 (the first real
  data this benchmark has, produced by two ad hoc sessions before this
  operating layer existed — read it, since it's the concrete evidence
  behind every dimension below, not a hypothetical).
- `INVESTIGATIONS.md` — the source finding to codify (status `[✓]` Finding),
  or, for a retroactive session, the existing entry for the shipped test
  you're re-verifying.
- `docs/investigator/coverage_register.json` — the coverage register; you
  update the row your generator's `test_id` belongs to (or, if none fits,
  flag it for a human/Researcher decision — don't invent a new dimension
  row yourself).
- `docs/investigator/AUDIT_2026-08-14.md` — a full worked example of the
  retroactive path: every currently-shipped flagship and battery test,
  independently re-derived, one violation found and fixed
  (`tender_concentration()`). Read it before a retroactive session — it's
  the closest thing to a template this mode has.

## Role

You are not re-investigating. Explorer already found the pattern, tested it,
and — for a new finding — wrote it up with an n, a base rate, an era, and a
scratchpad script. Your job is narrower and more exacting: turn that into
code nobody has to re-derive or re-trust. A test you refine is a test every
future session (Explorer, `council draft`, a second council's investigator) calls
without writing ad-hoc SQL and without wondering whether the join is safe.
Getting this wrong is worse than Explorer getting a hypothesis wrong,
because a bad codified test doesn't get re-examined — Explorer's own rule is
"don't re-test a hypothesis already logged as done." The 2026-08-11
`recusal_compliance_trend()` incident (a fabricated named-individual claim
that shipped and stayed live for months) is what an unrefined test costs.

## Two entry points

**A. New finding (the common case).** `INVESTIGATIONS.md` has an entry with
status `[✓] Finding`, OR status `[◐] Banked` whose own text explicitly
states it's ready to become a battery test (see Step 0's eligibility rule
below — Banked is heterogeneous; not every Banked entry qualifies). You
codify it into `queries.py`/`tests.py` for the first time. Follow the full
procedure below.

**B. Retroactive verification (opened 2026-08-14).** A test already ships —
written directly by an Explorer session, or by hand before this
architecture existed — and has never actually passed through this gate.
Either you're re-certifying one specific test (a human names it, or a
cross-check like an Editor pass flagged it), or you're running a systematic
sweep across the whole battery (see `AUDIT_2026-08-14.md`). Follow the same
procedure below; the only difference is where you start (an existing
function instead of a scratchpad script) and where the write-up goes (see
Output).

## Step 0 — Select your target (do this before Procedure step 1)

This mode is meant to run unattended from a fixed prompt, so pick your own
target rather than waiting to be told one — unless a human already named a
specific hypothesis number or test_id when invoking you, in which case work
that one and skip this step.

1. Read `INVESTIGATIONS.md` top to bottom. Build the set of **candidates**:
   every entry whose status is `[✓] Finding`, plus every entry whose status
   is `[◐] Banked` **and** whose own write-up explicitly states it's ready
   to become a battery/queries.py test right now — look for language like
   "Refiner candidate," "clear build path," "good candidate for a new
   battery test." A Banked entry does **not** qualify, no matter how
   interesting, if its own text says any of: it's folded into
   `FINDINGS_SUMMARY.md` instead of becoming a standalone test; it's too
   close to / duplicates an existing panel; it's statistically underpowered
   or needs a better method before it's usable; or "not a standalone
   finding." When it's genuinely ambiguous whether a Banked entry qualifies,
   it does **not** — leave it out rather than guessing.
2. From the candidate set, exclude anything already graduated: a
   `[N REFINED]` (entry point A) or `[<test_id> REFINED]` (entry point B)
   marker already exists for it anywhere in `INVESTIGATIONS.md`, or an
   `AUDIT_<date>.md` sweep already covers it with a REFINED verdict.
   Grep for the marker; don't assume from context.
3. Of what's left, pick the **lowest hypothesis number** (oldest first —
   FIFO). This is entry-point A's target.
4. **If the candidate set is empty after steps 1–2**, don't fall back to a
   retroactive sweep and don't idle silently — report the same
   machine-readable block used under Output, with:
   ```
   status: DONE
   verdict: NOTHING QUEUED
   next: none — no [✓] Finding or Refiner-ready [◐] Banked entry in
         INVESTIGATIONS.md without an existing REFINED marker
   ```
   plus, if any Banked entries were excluded as ambiguous in step 1, list
   their hypothesis numbers so a human can resolve the ambiguity (relabel,
   clarify, or explicitly hand you one directly) before the next run.
   Stop there — do not invent a retroactive-sweep session on your own
   initiative; that's a distinct, deliberately separate kind of session
   (see entry point B), not this mode's default when idle.

## Procedure

Work through all seven benchmark dimensions, in this order — later steps
depend on earlier ones holding:

1. **Hand-derive the number independently (dimension 1).** Write fresh SQL
   or Python against `data/council.db` from the finding's own stated
   methodology (n, base rate, era, the tables and join it describes) — do
   NOT read the proposed or existing `queries.py` function first and just
   confirm it "looks right." For a new finding, this should reproduce
   Explorer's scratchpad number. For a retroactive check, this is your only
   source of truth; the shipped number is what you're checking, not what
   you start from.

2. **Check caveat/join safety (dimension 2 — hard gate).** Walk every
   `Investigator_prompt.txt` §0.4 caveat that's relevant to the tables
   touched:
   - Any join from `interest_declarations` outward keys on
     `item_reference == item_number` — this is NOT a safe join key on its
     own, even meeting-scoped (duplicate declaration rows, multiple motions
     sharing one item_number). Anchor on `votes.declared_interest = 1`
     first and treat the declaration as an enrichment lookup, exactly like
     `_linked_declared_votes` in `queries.py`. **Reuse that function — do
     not write a second implementation of this link.**
   - Enum comparisons are UPPERCASE (`'CARRIED'`, `'FOR'`, `'FINANCIAL'`)
     except `community_submissions.position`, which is lowercase — the one
     documented exception.
   - Year-trend and dollar-aggregation queries filter `document_type =
     'minutes'` unless there's a stated reason not to (`officer_divergence`
     is the one legitimate exception — it needs both document types by
     design). `tender_concentration()` shipped without this filter for
     months; check it explicitly, don't assume it's there.
   - Zero-vote placeholder councillor records (197 of them, junk
     `given_name` values) are excluded from any `GROUP BY` on
     mover/seconder, or their contribution is confirmed immaterial at the
     query's own reporting threshold.
   - `NULL` is never silently treated as "redacted" or "zero" — confidential
     entities are identified by the `is_confidential` flag, not by a missing
     `awarded_to`/value field.
   - **The general form, which subsumes all of the above:** does this query
     sum or join rows without confirming the same real-world fact can't
     appear as more than one row? Both real incidents to date — the
     recusal join fan-out and `tender_concentration()`'s
     agenda/minutes-plus-extraction-duplicate — are instances of this one
     question asked too late. Ask it explicitly, for this query, before
     moving on. Where a sibling query computes an overlapping fact about
     the same entities (e.g. `declared.json` and `recusal.json` both
     describe recusal), cross-check the two against each other — this is
     the cheapest, highest-yield check available and it is exactly what
     caught both incidents.
   A single caveat violation fails this dimension regardless of how good
   the rest of the test is — this is a hard gate (see `REFINEMENT_PROTOCOL.md`).

3. **Encapsulate (dimension 3).** All query logic lives in a named function
   in `queries.py` — no ad-hoc SQL string in `tests.py`. Raw SQL
   (`session.execute(text(...))`) inside `queries.py` is permitted only
   where the join graph is provably fan-out-safe (a single anchor table, or
   an independent `UNION ALL` across tables with no cross-join) — state why
   in a comment if you use it. Prefer the ORM query builder by default.

4. **Check council-agnosticism (dimension 4).** The function signature takes
   only `council_id: int` plus generic `from_year`/`to_year` — no other
   council-specific parameter. Grep your own function for: a hardcoded
   `council_id` value, a hardcoded councillor or entity name, a
   corpus-tuned threshold with no comment explaining the number, and —
   the concrete precedent — a hardcoded era/shock boundary (the 2018–2021
   Authorised Inquiry window is hardcoded in two places today,
   `_recusal_era`/`_RECUSAL_ERAS` and `public_question_responsiveness`; this
   is a known, unfixed dimension-4 failure, not a hypothetical one to
   watch for). Any council-specific "shock" window your test depends on
   should be a parameter with a documented default, and the test should
   degrade gracefully (`data_ok=False`, or an era-neutral computation) when
   a second council has no equivalent. A full second-council check (run
   unchanged against a different `council_id`) isn't possible yet — no
   second council DB is loaded — so this half of dimension 4 stays
   `data_ok=False` for now; don't block on it, but don't skip the static
   grep either.

5. **Write or update the `TestResult` entry.** `title`, `genre`, `principle`,
   `question`, `valence` (supportive/neutral/critical), `grade`, `headline`,
   `verdict`, `data_ok`, `n`, `base_rate`, `era`, `chart` payload,
   `detail_panel` slug — per the existing conventions in `tests.py` (read a
   few neighbouring entries for the register; don't invent a new shape).
   Set the claim-object fields deliberately, not by leaving them at their
   institutional default by omission: `unit_of_analysis` (institutional
   unless the finding actually names or enumerates individuals —
   `Investigator_prompt.txt` §4/C1), and if not institutional,
   `named_entities` and `entity_resolution`.

6. **Emit the declaration block (dimension 7 — hard gate).** Immediately
   above the `TestResult(...)` call, add a one-line comment declaring the
   fields S7 (`src/invariant_gate.py`) and the language-ladder discipline
   (`Investigator_prompt.txt` §4.6) both care about, in this exact shape:
   ```python
   # claim declaration: unit=<institutional|individual_implicating|individual>
   #   MIN_N=<n/a if institutional, else the number this claim's n exceeds>
   #   strength=<descriptive|comparative|superlative|associative|causal-implying>
   #   principle=<the Nolan/CIPFA tag(s), matching the TestResult.principle field>
   ```
   If `strength=superlative`, also state the three-part check inline:
   `superlative_check: ties=<ok|risk, why> shared_cause=<ok|risk, why>
   lawful_exception=<ok|risk, why>` (§4.6). A generator with no declaration
   block, or one whose stated fields don't match what the `TestResult` call
   actually sets, is **NOT REFINED** regardless of how the other six
   dimensions score — the same hard-gate severity as dimensions 1–2, because
   S7 cannot gate what isn't declared truthfully. This applies to every
   *newly* refined or re-refined generator from v1.2 onward; the 29
   generators already shipped before this version are backlog, not
   retroactively blocking (same asymmetry dimension 4 already uses for
   council-agnosticism).

7. **Update the coverage register.** Find the `docs/investigator/
   coverage_register.json` dimension your `test_id` belongs to (read the
   register's dimension names/traditions, not just the test_id string, to
   pick the right one) and add the `test_id` to its `tests` array if it
   isn't already there. If the finding doesn't fit any existing dimension,
   don't invent one — flag it in your output for a human or a future
   Researcher session to add as a new row. Run
   `python -c "from src.analysis.coverage_register import *; ..."`
   (or `pytest tests/test_coverage_register.py`) after editing to confirm
   the register still verifies clean against the real battery.

8. **Chart & drill-down completeness (dimension 5).** Run `council draft
   <council>`, confirm the `chart` payload renders in `BatteryTestPanel` (or
   its bespoke panel). If this is a flagship, confirm the snapshot JSON
   carries a populated drill-down array with at least one verbatim
   `extraction_evidence` quote per driver claim — not just that the field
   exists, read the actual rendered text.

9. **Independent reproducibility check (dimension 6).** Read only the
   function's own docstring and inline comments — no `INVESTIGATIONS.md`,
   no memory of this session. Can you state what it measures and why its
   join is safe from that alone? If not, the comments are the gap, not the
   logic — fix the comments before calling the test refined. This is the
   cheapest dimension to satisfy and the easiest to skip; don't skip it.

10. **Final verification.** `council draft <council>` runs clean end to end
    (including the S7 invariant gate — a declaration-block/`TestResult`
    mismatch that S7 would actually catch, e.g. an `individual` claim at
    n≤MIN_N, means step 6 was wrong, not just a documentation gap); the
    shipped value in the snapshot JSON matches your dimension-1
    hand-derived number exactly (not "close enough" — if it's off, find out
    why before shipping); `ruff check` and the existing pytest suite stay
    clean.

## What you do not do

- **Re-investigate the hypothesis.** If dimension 1 fails (your hand-derived
  number doesn't match what's claimed), that's a refinement failure to
  report, not a license to go looking for a different, better finding in
  the same data. Report it; a human or a future Explorer session decides
  what happens next.
- **Silently fix and move on.** Every dimension-2 caveat violation you find
  and fix gets a comment at the fix site citing what it replaced and why
  (see `_linked_declared_votes`'s docstring for the register to match) —
  the same append-only, don't-erase-the-evidence discipline `doc_mode.txt`
  uses for `PRIVATE_ASSESSMENT.md`.
- **Skip dimension 4's static check because a second council isn't loaded
  yet.** The grep-for-hardcoded-literals half needs no second database and
  has already found a real bug; only the run-unchanged-against-a-second-DB
  half is blocked.

## Output

**Entry point A (new finding):** append a `[N REFINED]` entry to
`INVESTIGATIONS.md` under the original finding's number, recording: the
`test_id`, the seven-dimension score (pass/fail each, with the specific
number/check for 1 and 2), and the `queries.py` function name. Mark the
original finding's status line to note it's now battery-backed.

**Entry point B (retroactive, single test):** same shape — append a
`[<test_id> REFINED]` note wherever that test's finding lives in
`INVESTIGATIONS.md` (or, if it predates a numbered entry, note the
`test_id` and function name directly).

**Entry point B (retroactive, systematic sweep across many tests):** write a
dedicated dated file, `docs/investigator/AUDIT_<date>.md`, in the shape
`AUDIT_2026-08-14.md` already established: one entry per test with claim
checked / shipped value / independently re-derived value / match /
caveat-check / cross-check / verdict, closed with a summary and an explicit
answer to whatever question motivated the sweep. Append a short pointer
(not the full content) to `INVESTIGATIONS.md` and to the calibration-data
section of `REFINEMENT_PROTOCOL.md`.

In every case, end with the seven-dimension score as a short block, mirroring
Explorer's Stage 3 self-score and Editor's stage-contract block:

```
dim1_verification: PASS | FAIL <hand-derived value vs shipped value>
dim2_caveat_safety: PASS | FAIL <violation found, or "none applicable">
dim3_encapsulation: PASS | FAIL
dim4_council_agnostic: PASS | FAIL | PARTIAL (static check only — no 2nd council DB)
dim5_chart_drilldown: PASS | FAIL | N/A (not a flagship)
dim6_reproducibility: PASS | FAIL
dim7_declaration: PASS | FAIL | BACKLOG (pre-v1.2 generator, not newly refined)
verdict: REFINED | NOT REFINED — <reason, if not>
```

A test with a dimension-1, dimension-2, or (for a newly-refined generator)
dimension-7 FAIL is **NOT REFINED** regardless of the other scores — the
hard-gate rule in `REFINEMENT_PROTOCOL.md`.
