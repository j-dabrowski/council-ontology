COUNCIL ONTOLOGY — PROJECT OVERVIEW
=====================================
Generated: 2026-05-28


PURPOSE
-------
Data pipeline that turns City of Cambridge (WA) council meeting minutes PDFs into a
structured SQLite database, with the goal of analysing voting patterns, planning
decisions, and councillor behaviour over time.

Three-layer ontology:
  Semantic  — entities and relationships (councils, councillors, sites)
  Kinetic   — actions and events (motions, votes, planning applications)
  Dynamic   — feedback loops and emergent patterns (voting blocs, relationship edges)

PARTS OF THE PROJECT
=====================

1. SCRAPER — src/scraper/cambridge.py
--------------------------------------
Downloads minutes PDFs from the Cambridge council website using four sources:
  - Sitemap (1994–2021, comprehensive)
  - Playwright headless browser (2022+, primary — handles JS/Akamai)
  - Wayback Machine CDX API (2022+, fallback when Playwright not installed)
  - Site search (live tail: most recent ~10 meetings)

Output: data/raw/cambridge/*.pdf + data/raw/cambridge/manifest.json
  manifest maps filename → { meeting_date, meeting_type }

Browse what's been downloaded:
  council status
  council docs cambridge
  council docs cambridge --filter pending
  council docs cambridge --filter no-manifest
  ls data/raw/cambridge/*.pdf | wc -l
  cat data/raw/cambridge/manifest.json | python -m json.tool | head -60


2. CENSUS — scripts/census.py  [Level 0]
-----------------------------------------
Runs once across all PDFs. No LLM calls. Pure text extraction and keyword scanning.

For each PDF:
  - Extracts text via pypdf
  - Counts keyword hits across 7 groups: motions, votes, planning, interests,
    community, budget, procedural
  - Detects section headers (numbered items, uppercase headings)
  - Estimates entity counts (motions, planning items, interest declarations)
  - Assigns size bucket (tiny/small/medium/large/failed) and decade
  - Flags outliers (empty, zero keywords, high DA count, etc.)

Incremental by default (skips already-scanned PDFs). Parallel scanning via
ProcessPoolExecutor (default 8 workers, ~4 minutes for 537 PDFs).

Output:
  data/census.json         — per-document metadata, keyword counts, flags
  data/census_summary.txt  — aggregate stats and outlier list

Commands:
  council census cambridge
  council census cambridge --force    # rescan everything
  council census cambridge --workers 4
  python scripts/census.py cambridge  # standalone


3. INVENTORY — scripts/inventory.py  [Level 1]
------------------------------------------
Runs once across all PDFs. One cheap Haiku call per document.

Purpose: not to extract every detail, but to answer — what kind of document
is this, and roughly what does it contain?

For each PDF:
  - Builds a text window: first 20,000 chars + last 10,000 chars. For docs
    under 30,000 chars, the full text is used. A separator marks omissions.
  - Sends the window to Haiku with a lightweight inventory-only prompt
    (src/extraction/inventory_prompt.txt).
  - Returns: meeting date/type, list of section headings, and approximate
    counts of motions, planning items, interests, petitions, budget items,
    and other content.
  - Caches raw LLM responses in .cache/llm_responses/ by document hash +
    prompt version. Re-running with the same prompt version is free.
  - Cross-references with Level 0 census counts and flags disagreements.

Incremental by default (skips docs with existing ok-status inventory files).
Parallel via ThreadPoolExecutor (up to 20 concurrent API calls).

Output:
  data/inventories/{stem}.json   — per-document inventory
  data/inventories/summary.json  — aggregate: meeting type distribution,
                                   average counts, flagged documents

Commands:
  council inventory cambridge
  council inventory cambridge --limit 10
  council inventory cambridge --force    # re-run even if inventory exists
  python scripts/inventory.py cambridge  # standalone


4. EXTRACTOR — src/extraction/
--------------------------------
  extractor.py      — sends PDF text to Claude, parses JSON response
  schemas.py        — Pydantic models for extraction output (deliberately lenient)
  system_prompt.txt — full extraction instructions and output schema

Pipeline:
  PDF → pypdf text extraction → truncate to 80,000 chars → Claude API call
  → strip markdown fences → Pydantic validation → save_extraction(text=) → DB
  → extraction_evidence rows (source quotes resolved to char offsets)

Current model: claude-haiku-4-5-20251001 (Sonnet/Opus also supported)
Max tokens: 64,000 output (streams to avoid truncated JSON)
Retry: 3 attempts with exponential backoff on connection/status errors

Schema extracts:
  - council name, meeting date/type, location
  - councillors present/apology
  - motions (motion text, outcome, mover, seconder, individual votes, planning
    application with community submissions, tags)
  - public_questions, deputations, petitions, appointments
  - committee_reports, budget_items, interest_declarations, tenders
  - delegated_decisions, building_permits
  - other_items (catch-all for genuinely unclassifiable content)

Browse what's been extracted:
  council status
  sqlite3 data/council.db "SELECT meeting_date, meeting_type FROM meetings ORDER BY meeting_date DESC LIMIT 20"
  sqlite3 data/council.db "SELECT COUNT(*) FROM motions"
  sqlite3 data/council.db "SELECT COUNT(*) FROM votes"
  cat data/extraction_errors.json


5. DATABASE / ONTOLOGY — src/models/ontology.py
-------------------------------------------------
SQLite at data/council.db. Tables:

  Semantic layer:
    councils          — council registry (name, short_name, website)
    councillors       — persons who have voted (given_name, family_name, slug)
    councillor_terms  — tenure per council (ward, role, term_start/end) [NEVER POPULATED]
    sites             — physical addresses from planning applications

  Kinetic layer:
    meetings              — one row per meeting (date, type, location, pdf_path)
    motions               — formal motions (text, outcome, mover, seconder, tags)
    votes                 — individual councillor votes (for/against/abstain/absent)
    planning_applications — DA/DV details (reference, address, applicant, status, value)
    community_submissions — public submissions on planning applications
    public_questions      — questions asked during Public Question Time
    deputations           — formal presentations by members of the public
    petitions             — petitions tabled at meetings (subject, signatory count)
    appointments          — councillor appointments to external bodies
    committee_reports     — standing committee reports tabled
    budget_items          — financial/budget information items
    interest_declarations — declared financial/impartiality/proximity interests
    tenders               — tender evaluations and procurement decisions
    delegated_decisions   — decisions made under officer delegation
    building_permits      — building permit/licence information items
    other_items           — catch-all for content not fitting dedicated fields
    extraction_evidence   — verbatim source quotes per entity with char offsets
                            (char_offset=None flags quotes not found in source text)

  Dynamic layer:
    relationships  — typed edges between any entities [ALWAYS EMPTY — not yet populated]
      RelationshipKind values: ALLY, OPPONENT, COALITION, DECLARED_INTEREST,
                               AMENDS, SUPERSEDES, RELATES_TO, SUBJECT_OF

Useful DB queries:
  sqlite3 data/council.db ".tables"
  sqlite3 data/council.db "SELECT outcome, COUNT(*) FROM motions GROUP BY outcome"
  sqlite3 data/council.db "SELECT c.given_name, c.family_name, COUNT(v.id) as n FROM councillors c JOIN votes v ON v.councillor_id=c.id GROUP BY c.id ORDER BY n DESC LIMIT 10"
  sqlite3 data/council.db "SELECT pa.reference_number, pa.status, s.address FROM planning_applications pa LEFT JOIN sites s ON s.id=pa.site_id LIMIT 20"
  sqlite3 data/council.db "SELECT meeting_date, meeting_type, id FROM meetings ORDER BY meeting_date DESC LIMIT 20"


6. CLI — src/cli.py
---------------------
All commands are invoked as: council <command>  (or: python -m src <command>)

  — PIPELINE —

  council run cambridge [--limit N] [--since-year YYYY]
      Full pipeline: scrape → extract → save to DB.

  council scrape cambridge [--since-year YYYY]
      Download PDFs only, no Claude calls.

  council extract cambridge [--limit N] [--from-year YYYY] [--to-year YYYY]
                            [--files a.pdf b.pdf ...] [--force]
      Process already-downloaded PDFs. --files targets specific PDFs.
      --force re-extracts PDFs already in the DB.

  council status
      Pipeline summary and per-year breakdown for all councils.

  council docs cambridge [--filter all|pending|ingested|no-manifest]
      Per-file table: filename, date, type, manifest ✓/–, DB ✓/pending, meeting ID.

  — SCRIPTS —

  council census cambridge [--force] [--quiet] [--workers N]
      Level 0: keyword scan across all PDFs. Outputs data/census.json and
      data/census_summary.txt. Incremental by default; --force rescans everything.
      Uses parallel workers (default: min(8, cpu_count)).

  council inventory cambridge [--limit N] [--force] [--quiet]
      Level 1: one cheap Haiku call per document. Builds a text window (first 20k
      chars + last 10k chars) and asks: what kind of document is this, and roughly
      what does it contain? Caches LLM responses in .cache/llm_responses/. Outputs
      data/inventories/{stem}.json and data/inventories/summary.json.

  council typology cambridge [--quiet] [--limit N] [--history]
      Level 1→2: analyse inventory typology. Reads all data/inventories/*.json and
      produces data/{council}_typology_review.txt. Run after Level 1 inventory and
      before making any Level 2 schema decisions. Surfaces meeting type distribution,
      inventory field prevalence (docs/% for each count field), entity counts by
      decade, other_content patterns, section heading gaps, and census cross-reference
      flags. Saves quality score to data/inventory_quality/ on each run.
      --limit N: analyse only the N most-recently-updated inventory files (for sampling).
      --history: print quality score trend over time.

  council sample cambridge [--count N] [--output-file PATH]
      Level 3a: select a stratified 15-20 doc sample from census + L1 flags.
      Stratifies by era, size bucket, meeting type, and outliers.
      Always saves canonical selection to data/{council}_sample.json.
      Also prints filenames to stdout.

  council extract-sample cambridge
      Level 3b: extract the saved sample. Reads data/{council}_sample.json.
      Always runs with --force (re-extracts regardless of DB state); warns user.
      Run after 'council sample' to populate extraction_evidence for 3c.

  council validate-sample cambridge
      Level 3c: validate sample extractions. Reads data/{council}_sample.json.
      Queries extraction_evidence for hallucination rate and coverage ratio.
      Diffs entity counts against L1 inventory. Detects keyword gaps.
      Writes data/sample_validation/ report. Gate before Level 4.
      (scripts/validate_sample.py — PENDING)

  council batch cambridge [--limit N] [--model MODEL] [--from-year YYYY]
                          [--to-year YYYY] [--files a.pdf b.pdf ...] [--force]
      Batch extraction with structured error report. Preferred over 'extract'
      for bulk runs. Writes error breakdown to data/extraction_errors.json.

  council eval [--quick] [--compare] [--show] [--history] [--no-save]
      Evaluate prompt quality across benchmark PDFs (4 PDFs × 2 models).
      --quick: one sticky PDF until all models score 95+, then rotate.
      --compare: show delta vs previous run. --show: print latest (no API calls).
      --history: score trend across all saved runs.

  council compare <pdf.pdf> [--council cambridge] [--no-save]
      Run all three models (Haiku/Sonnet/Opus) on one PDF and print a
      side-by-side comparison. Does not write to the DB.

  council costs [--from-year YYYY] [--to-year YYYY] [--max-chars N|full] [--quiet] [--show]
      Estimate Anthropic API cost for pending PDFs without making any API calls.
      --show: print the last saved estimate.

  — ANALYSIS —

  council analyse cambridge <query> [options]
      Run analysis queries against the DB. Queries:
        councillors              — all councillors sorted by vote count
        alignment                — pairwise voting agreement (--min-shared, --limit)
        contested                — carried motions with opposition (--min-against, --limit)
        planning                 — top sites by application count (--limit)
        councillor --name NAME   — one councillor's vote summary (partial family name)
        motions --tag TAG        — motions filtered by tag (--limit)

  — OPTIONS —

  council -v <command>
      Enable verbose (DEBUG) logging. Applies to all commands.
      All runs also write DEBUG logs to council.log.

8. ANALYSIS — src/analysis/queries.py + council analyse
---------------------------------------------------------
Query helpers exposed via `council analyse <council> <query>`.

  council analyse cambridge councillors
      All councillors seen in votes, sorted by vote count.

  council analyse cambridge alignment [--min-shared N] [--limit N]
      Pairwise voting agreement matrix. Green ≥85%, yellow 50-85%, red <50%.
      --min-shared filters out pairs with too few shared votes (default: 5).

  council analyse cambridge contested [--min-against N] [--limit N]
      Motions that carried but had meaningful opposition (default: ≥2 against).

  council analyse cambridge planning [--limit N]
      Top sites by number of planning applications.

  council analyse cambridge councillor --name <family-name>
      One councillor's vote summary: totals, dissent rate, declared interests.
      Partial family name match (e.g. --name Brad).

  council analyse cambridge motions --tag <tag> [--limit N]
      Motions filtered by LLM-assigned tag (e.g. planning, budget, governance).

Underlying library functions (callable from Python directly):
  get_council_by_name, list_councillors, meetings_in_range, motions_by_tag,
  planning_motions, contested_motions, voting_alignment_matrix,
  councillor_vote_summary, top_planning_sites


WHAT IS UNFINISHED

1. EXTRACTION BACKLOG (341 PDFs)
   Most years have only a handful ingested — the bulk of the archive is pending.
   Levels 0–2 and Level 3a/3b are complete. Next: Level 3c (validate-sample),
   then Level 4 (confidence metrics), then Level 5 (full batch).
   See PIPELINE.md and IMPLEMENTATION_ANALYSIS.md for the full sequence.
     council validate-sample cambridge    # Level 3c — next step
     council batch cambridge --limit 20   # after Level 3c and 4 are done

2. DYNAMIC LAYER IS EMPTY
   The relationships table and RelationshipKind enum are fully modelled.
   voting_alignment_matrix() in queries.py computes pairwise agreement in memory.
   Nothing ever writes to the relationships table.
   Next step: script that thresholds alignment scores and persists edges
     (e.g. agreement_rate > 0.85 → ALLY, < 0.40 → OPPONENT).

3. COUNCILLOR_TERMS NEVER POPULATED
   The model has ward/role/term dates per councillor per council.
   Councillors are created from vote records only — no ward, no role, no dates.

4. THREE MEETING FIELDS ALWAYS NULL
   minutes_pdf_url  — source URL is in the manifest but never written to DB
   minutes_text     — raw extracted text is discarded after extraction
   extracted_at     — timestamp is never set

5. LONG DOCUMENTS SILENTLY TRUNCATED
   extractor.py only processes chunks[0] (first 80,000 chars).
   Comment says "future: merge multi-chunk results".
   Some older/longer PDFs may be missing agenda items from the second half.
   Note: census shows 319/537 documents exceed 200k chars — truncation is significant.

6. NEW SCHEMA FIELDS — PERSISTED (done 2026-05-29)
   11 new DB tables added to ontology.py and wired into save_extraction():
   public_questions, deputations, petitions, appointments, committee_reports,
   budget_items, interest_declarations, tenders, delegated_decisions,
   building_permits, other_items.
   Appointments and interest declarations resolve councillors via the
   councillors table. Tables are created automatically by create_all().

7. ONLY ONE COUNCIL
   The COUNCILS dict in cli.py has a single entry with a "add new councils here"
   comment. The full architecture supports multiple councils.
